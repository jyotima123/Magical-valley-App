# 1.6.18

- Performance: vehicle photos in the **Cars** tab are now downloaded once and served from disk from then on — across scrolls, across screens and across app launches. Previously every photo was re-fetched constantly
- Scrolling the list, opening a car and swiping its gallery, then coming back, no longer re-downloads a single byte; the same is true after killing and relaunching the app
- Photos below the fold are pulled down ahead of the scroll, so a page revealed mid-fling paints from cache instead of popping in one card at a time

# Detailed Changes

### Why the photos were reloading

The cars screens used `Image.network`, which only ever hits Flutter's in-memory `ImageCache`. That cache is capped (~100 MB / 1000 entries), evicts under pressure as you scroll a long inventory, and is wiped on every app launch — so photos were re-fetched over and over. `cached_network_image` was already a dependency and already used by chat, channels and ads; the cars screens simply were never wired up to it.

### Vehicle photo cache (`lib/modules/cars/vehicle_image.dart`, new)

- `VehicleImageCache.instance`: a dedicated `CacheManager` with its own folder and metadata database, so vehicle photos are evicted independently of every other cached image in the app
- Sized for a real inventory: `stalePeriod` 365 days and `maxNrOfCacheObjects` 1000, against package defaults of 30 days / 200 files — the defaults would evict listings the user is still scrolling past
- `_ImmutableFileService`: `flutter_cache_manager` normally honours the CDN's `Cache-Control` header (falling back to 7 days), then revalidates each expired file with an `If-None-Match` round trip. A car's photos are immutable — the feed can change *which* URLs a listing points at, but the bytes behind any one URL never change — so every response is wrapped to report `validTill` a year out. Once a photo is on disk there is no network call at all for it, whatever headers the dealer's CDN sends
- `VehicleImage`: drop-in replacement for `Image.network` on the cars screens, with `placeholder` / `errorWidget` builders and an optional `decodeWidth`
- `VehicleImageCache.prefetch(urls)`: warms the disk cache without building widgets. Already-cached URLs cost nothing and failures are ignored, since the widget retries when it actually renders

Deliberately **not** using `maxWidthDiskCache`: that option stores a resized file under a different disk key, which would make the list thumbnail and the detail photo two separate downloads of the same image. `decodeWidth` (`memCacheWidth`) only downsizes the decode in memory, so both screens share one file on disk — a car opened from the list shows its first photo instantly.

### Cars list (`lib/modules/cars/vehicles_screen.dart`)

- Card thumbnails render through `VehicleImage` with `decodeWidth: 800`, so a 4000px dealer photo is no longer decoded at full size into memory for a 180px-tall card
- `_prefetchThumbnails()` (new): pulls the thumbnails for the visible rows plus one page ahead onto disk. Called after a load or background refresh, after a search/chip/filter change, and when the next page is revealed on scroll

### Vehicle detail (`lib/modules/cars/vehicle_detail_screen.dart`)

- The gallery carousel renders through `VehicleImage`
- `initState` prefetches the whole gallery — `PageView` only builds the current page, so without this each swipe waited on its own download

### Add / edit vehicle (`lib/modules/cars/add_vehicle_screen.dart`)

- Upload previews render through `VehicleImage`, so re-entering the edit screen doesn't re-fetch photos already on disk

### Dependencies (`pubspec.yaml`)

- `flutter_cache_manager: ^3.4.1` promoted from a transitive dependency to a direct one, since the cache configuration now imports it

### Verification

- `flutter analyze lib/` reports 0 errors and 0 warnings; the remaining infos are all pre-existing `withOpacity` deprecations

# Notes

- Out of scope, deliberately: `Image.network` in `vehicle_inquiry_chat_screen.dart` (chat attachments) and the admin screens. Chat images are user uploads with a different lifecycle and are not part of the Cars browsing path
- The first run after upgrading still downloads each photo once — that's the point at which the cache is populated. Clearing the app's storage resets it, as with any on-device cache
