# 1.6.17

- Feature: vehicle inquiry chats (buyer ↔ seller conversations about a community listing) now appear in the main **Messages** tab alongside organization conversations, merged into one recency-sorted list instead of being reachable only from a listing's own inquiries screen
- Feature: dealer vehicle listings now have a **Message Dealer** button that opens an in-app conversation with the dealership, replacing the "View at Dealer" link out to the dealership's own website
- Buyers and dealers talk in the same chat, inbox and push notifications community listings already use — nothing hands the buyer off to an external site, phone dialler or email app
- Which account answers a feed's messages is configured once per feed in the new `dealer_sources` table, not per vehicle — confirmed against a live LiftKit response that a vehicle payload carries no email/phone/seller field at any level, matching the LiftKit docs; LiftKit mirrors a single dealership's inventory, so one account covers every vehicle from that feed
- Architecture is multi-provider ready: wiring up each of the next inventory providers is one `VehicleSource` value, one `vehicle_listings_source_check` value and one `dealer_sources` row, no other code changes

# Detailed Changes

### Vehicle inquiries in Messages (`lib/modules/chat/direct_messages_screen.dart`)

- `_loadVehicleInquiries()`: fetches `ApiRepository.getVehicleInquiries(userId)` (buyer- or seller-side conversations) every time org conversations load or refresh (initial load, pull-to-refresh, after sending/starting a DM); failures are silent so a vehicle-inquiry hiccup never blocks the org DM list
- `_InboxEntry` (new): thin wrapper around either a `DirectMessageConversation` or a `VehicleInquiryConversation` so both can be merged into one list and sorted by most recent activity (`_inboxEntries`); the plain (non-grouped) inbox list now renders from this merged list instead of org conversations alone, and the empty-state / empty-check both account for vehicle inquiries too
- Admins managing more than one organization get a grouped-by-org view; vehicle inquiries aren't tied to any managed org (listings belong to the admin personally), so they get their own trailing **"Vehicle Inquiries"** section appended after the org groups
- `_buildVehicleInquiryTile()` (new): shows the other participant's name, an unread dot, the vehicle photo as the avatar (car-icon fallback when there's no photo), the vehicle title on its own line so it reads as distinct from an org chat, and the last message preview; tapping pushes the existing `VehicleInquiryChatScreen`
- Search now also matches vehicle inquiries by the other participant's name or the vehicle title (`_filteredVehicleInquiries`)
- Dealer conversations land here through the same path — no separate inbox, tile or notification route for them
- Scoped out for now: no realtime subscription or in-app banner for new vehicle-inquiry messages while sitting on the Messages tab — push notifications already cover that via the existing FCM path (`openVehicleInquiryConversation`); tapping a vehicle inquiry always full-screen-pushes rather than populating the wide-screen split pane, which stays typed to `DirectMessageConversation`

### Dealer messaging schema (`migrations/076_dealer_inquiry_messaging.sql`, new)

Two things blocked reusing the existing inquiry system for feed vehicles: `vehicle_inquiry_conversations.vehicle_id` is a FK into `vehicle_listings` (feed vehicles live only in the provider's API, with ids like `liftkit:PG205293`), and `seller_id` must be a real `user_profiles` row (a feed carries no per-vehicle seller). Both are fixed at the database level so every consumer downstream keeps working untouched:

- `vehicle_listings` gains `source` (`community` | `liftkit`, CHECK-constrained) and a unique `external_id`. A feed vehicle is materialized into the table on first contact — a **shadow row** — after which the conversations view, the notification trigger and the Messages tab all work with no changes at all. It doubles as a snapshot: a conversation still shows what was being discussed after the car leaves the feed
- Stock and VIN uniqueness moved from global to `UNIQUE (source, …)`: our community stock counter (1001+) and a dealership's own stock numbers share a namespace and would otherwise collide, and the same VIN can legitimately appear in two feeds
- `dealer_sources` (new table): maps a feed to the account that receives its messages, plus `display_name` and an `is_active` kill switch. Readable by any signed-in user (the app checks "am I this feed's dealer?"), superadmin-writable
- `create_or_get_dealer_vehicle_inquiry(p_source, p_external_id, p_vehicle)` (new RPC): resolves the seller from `dealer_sources`, upserts the shadow row, then creates or returns the buyer's conversation. `SECURITY DEFINER` for two reasons — a buyer isn't an admin and so cannot insert into `vehicle_listings`, and the seller must be resolved server-side rather than taken from a client that could name anyone. Refuses a buyer who is the dealer, a `community` source, and a feed with no account configured (a distinct error, since that's an operator task and not a bug)
- Vehicle fields are read defensively out of the jsonb payload: a condition the feed words its own way is clamped to what `vehicle_listings_status_check` accepts rather than failing the insert

### Vehicle detail (`lib/modules/cars/vehicle_detail_screen.dart`)

- `_buildDealerActions()`: now a single full-width **Message Dealer** button with a spinner/disabled state while the conversation opens
- `_openDealerChat()` (new): calls the RPC through `ApiRepository.createOrGetDealerInquiry()` and pushes the same `VehicleInquiryChatScreen` a community listing uses; errors from the RPC (notably "no dealer account is configured for this inventory yet") surface verbatim in a snackbar
- Removed `_openDealerPage()`, `_callDealer()` and `_emailDealer()` along with the `View at Dealer` / `Call Dealer` / `Email Dealer` buttons — a listing must not route a buyer to the dealership's website, dialler or inbox, since replacing that website is the point of listing here
- `lib/modules/cars/dealer_contact.dart` deleted: it existed only to build `tel:` / `mailto:` links from `.env_*`, and `LIFTKIT_DEALER_EMAIL` / `LIFTKIT_DEALER_PHONE` are gone from both env files with it

### Listing queries (`lib/modules/cars/vehicles_screen.dart`, `lib/modules/cars/add_vehicle_screen.dart`)

- The Cars list now filters community listings to `source = 'community'`. It already renders dealer inventory from the live feed, so an unfiltered query would show every contacted vehicle twice, the second copy stale
- `_generateStock()` is scoped the same way, so a dealership's stock numbers can't push our community counter up

### Model (`lib/modules/cars/vehicle_listing.dart`)

- `VehicleListing.fromJson` reads the new `source` column (defaulting to `community`, so rows written before migration 076 keep behaving as before), and `dealerSourceKey` exposes the value the RPC and `dealer_sources` key off

### Tests

- `test/dealer_inquiry_test.dart` (new, 8 tests): the feed key matches what `dealer_sources.source` stores, external ids are feed-namespaced and stable, the shadow-row payload carries every column the RPC inserts with a CHECK-valid status, and `source` round-trips through `fromJson` in both directions
- `test/dealer_contact_test.dart` deleted along with the code it covered
- `flutter analyze` reports no errors on the touched files; full cars suite green (8 new + `liftkit_vehicle_mapper_test.dart` 9 + `vehicles_screen_pagination_test.dart` 4 = 21 passing)
