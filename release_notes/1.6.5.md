# 1.6.5

- Fix Direct Messages conversation list not refreshing automatically after returning from a chat
- Fix own messages being shown as unread in the conversation list
- Make `UserSelectorScreen` always filter by `regular` users
- Created migration to allow admins to view regular users listings
- Created migration to allow admins message users instead of the other way
- Fix "Start chatting with" empty state showing organization name instead of user name on the admin side
- Add conversation-start banner ("This is the start of the conversation between…") at the top of every chat
- Add date separator pills between messages on different calendar days (Today, Yesterday, day name, or M/D/YYYY)
- Fix "Message" / "Open Chat" button not opening the conversation when tapped from the Explore or Channels screen

# Detailed Changes

### Direct Messages: conversation list not refreshing on back

When returning from a chat on narrow screens, the conversations list was not automatically updated with the latest last message or timestamp — requiring a manual pull-to-refresh. The fix adds a `_loadConversations()` call in the `Navigator.push(...).then(...)` callback of `_navigateToChatView`. To avoid flashing the loading spinner over an already-populated list, `_loadConversations` now only sets `_isLoading = true` when `_conversations` is empty (i.e. the first load); subsequent calls are silent refreshes.

### Direct Messages: own messages shown as unread

After sending a message and returning to the conversation list, the unread dot appeared on that conversation. This happened because `_saveLastReadTime` is called at the moment of navigation (before the message is sent), so any message sent afterward — including the user's own — has a `createdAt` timestamp newer than the stored read time, causing `_hasLocalUnread` to return `true`.

The fix checks whether the last message was sent by the current user before comparing timestamps. For regular users, "own" is `lastMessage.createdBy == _currentUserId`. For admins, messages they send appear attributed to the organization (`senderId != conversation.userId`), so the same logic used in `_getMessageSenderName` is applied: a message is "own" when `lastMessage.createdBy != conversation.userId`. If the last message is own, `_hasLocalUnread` returns `false` immediately.

### Direct Messages: "Start chatting with" shows wrong name for admins

The empty-state text in `_ChatScreenState` (narrow screen) always used `conversation.organizationName` regardless of role. For admins the correct counterpart is the user they are talking to, so it now mirrors the wide-screen logic: admins see the user's full name (falling back to username or "User"), regular users still see the organization name.

### Direct Messages: conversation-start banner

A `_ConversationStartBanner` widget was added and rendered as the first item (index 0) of every chat's `ListView.builder`, with messages starting at index 1. Both the wide-screen (`_buildChatViewContent`) and narrow-screen (`_ChatScreenState`) implementations were updated. The banner is always visible when the user scrolls to the top of the conversation, displaying: *"This is the start of the conversation between {user} and {organization}"*.

### Direct Messages: date separator pills

A `_formatDateLabel` top-level function mirrors `_formatMessageTime`'s bucketing logic to produce date labels: "Today", "Yesterday", the weekday name for the past 7 days, and `M/D/YYYY` for older dates. All comparisons use local time so day boundaries are correct for the user's timezone.

A `_buildChatItems` top-level function walks the message list and inserts a `DateTime` entry whenever the calendar day changes, returning a flat `List<Object>` of separators and messages. A compact `_ChatDateBanner` widget (rounded pill, 11px text) renders each separator. Both `ListView.builder` instances were updated to use the computed items list, so date pills appear automatically between messages on different days.

### "Message" / "Open Chat" button not opening the conversation

Tapping the button on an organization card (in the Explore or Channels screen) switched to the Direct Messages tab but did not open or create the conversation.

Two root causes were fixed:

1. **Admin branch passed no `organizationId`** — both `organizations_screen.dart` and `categories_grid_screen.dart` had an early-return path for admins that called `switchToDirectMessagesTab()` without an `organizationId`, so the DM screen had no conversation to open. Both `_startDirectMessage` methods were collapsed into a single path that always passes `organizationId: organization.id`, regardless of role.

2. **No role-aware open/create logic** — `switchToDirectMessagesTab` was wired to `openConversationWithOrganization`, which creates a conversation using `_currentUserId` as the user. That is wrong for admins (the admin's ID is not the conversation's user). A new `openOrCreateConversation(orgId)` method was added to `DirectMessagesScreenState`: for regular users it delegates to `openConversationWithOrganization`; for admins it skips the org-selection step, shows only the user-picker (org is already known from the card), then calls `createOrGetDirectMessageConversation(selectedUser.id, orgId)` and navigates into the conversation.

`switchToDirectMessagesTab` was updated to call `openOrCreateConversation` and now includes a 150 ms fallback retry in case the DM Navigator's state is not yet available in the first `postFrameCallback`.
