# Detailed Changes

### New edge function: `send-dm-notification`

A new Supabase edge function (`supabase/functions/send-dm-notification/index.ts`) handles push notifications for direct messages exclusively. The previous `send-fcm-notification` function is unchanged and continues to handle channel post notifications only.

Recipient logic:

- **User → org**: notifies all admins linked to the organization via `admin_organizations` where `user_profiles.role = 'admin'`. Superadmins are never notified.
- **Admin → user**: notifies only the conversation's regular user (`conversation.user_id`).

The notification FCM data payload carries `notification_type: "direct_message"` and `conversation_id`, which the app uses to deep-link into the correct conversation on tap.

### Migration 064: DB trigger re-routed (`migrations/064_dm_notification_dedicated_function.sql`)

The `notify_direct_message_created()` Postgres trigger function (originally from migration 046) previously called `send-fcm-notification` with `notificationType=direct_message` and looped through admins in SQL without filtering out superadmins. Migration 064 replaces it with a lean version that calls `send-dm-notification` with just `conversationId`, `senderId`, and `messageContent`. All recipient logic now lives inside the edge function.

This is also why the Flutter client (`supabase_api_service.dart`) no longer calls the edge function directly after inserting a message — the DB trigger is the single, authoritative notification source.

### In-app notification banner (`direct_messages_screen.dart`)

When the user is on the Direct Messages screen and a new message arrives in a conversation they are **not** currently viewing, a card slides down from the top of the screen with the sender's avatar, name, and a one-line message preview. The banner:

- Slides in and out with `AnimatedSwitcher` + `SlideTransition` + `FadeTransition`
- Auto-dismisses after 4 seconds
- Can be dismissed immediately with the × button
- Navigates straight into the conversation when tapped
- Is suppressed for the conversation currently open (narrow-screen push or wide-screen selection)
- Never shows for the user's own sent messages
- Is driven entirely by the existing Supabase Realtime conversations stream — no extra subscriptions or network calls

### Global in-app banner (`main_scaffold.dart`)

The DM notification banner now works on every tab, not just the Direct Messages screen. The root issue was that `DirectMessagesScreen` is kept alive in an `Offstage` widget when inactive — its Realtime subscription fired correctly, but the banner rendered invisibly. The fix routes the banner through `MainScaffold` when the user is on a different tab:

- `_onConversationsUpdated` checks `mainScaffoldKey.currentState?.selectedTabIndex`.
- **On the DM tab**: the existing in-screen banner in `DirectMessagesScreen` is shown as before.
- **On any other tab**: `mainScaffoldKey.currentState?.showDMBanner(...)` is called, which shows the banner inside `MainScaffold`'s Stack — always on top, always visible.

### Generic app banner / snackbar (`main_scaffold.dart`)

`showBanner()` is a new public method on `_MainScaffoldState` that shows a slide-down card over all content. It accepts full colour customisation, making it suitable for any alert type:

```dart
// Warning
mainScaffoldKey.currentState?.showBanner(
  title: 'Slow connection',
  body: 'Some content may not load.',
  icon: Icons.warning_amber_rounded,
  iconColor: Colors.amber,
  backgroundColor: const Color(0xFFFFFDE7),
  titleColor: const Color(0xFFF57F17),
);
```

Parameters: `title`, `body` (hidden when empty), `icon`, `backgroundColor`, `titleColor`, `bodyColor`, `iconColor`, `onTap`, `duration`. See `docs/APP_BANNER.md` for the full reference and common variants.

`dismissBanner()` is also public for programmatic dismissal.

### Foreground DM notification channel (`fcm_service.dart`)

`_showLocalNotification` now selects the Android notification channel based on `notification_type`. DM notifications use `dm_notifications`; post notifications continue to use `post_notifications`. This allows users to configure the two notification types independently in device settings.
